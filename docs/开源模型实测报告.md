# 开源模型实测报告

测试日期：2026-10-29。测试地点：当前 Windows 电脑，本地推理，无付费 API。

**结论：这套组合在当前电脑上具备足够的模型计算速度，但识别和翻译仍有明确错误，尚不能按“所有内容忠实准确翻译”验收。**

本轮完成的是电脑端模型实测。现有 Android APK 和后端默认模式没有改变，手机应用仍显示固定演示字幕，尚未接入下面的真实模型。

## 2. 样本与方法

### 语音识别

使用公开的 [japanese-asr/ja_asr.common_voice_8_0](https://huggingface.co/datasets/japanese-asr/ja_asr.common_voice_8_0) 测试分片，按文件顺序选择前 10 段时长在 2～15 秒的记录，合计 **49.08 秒**。没有按模型识别好坏挑选样本。

将音频解码为 16 kHz 单声道后输入模型，完整读取推理结果才停止计时；模型加载和首次预热单独统计，不混入后续推理耗时。

### 文本翻译

使用 10 组自行编写的短句，覆盖普通对白、否定、口语、粗口、成人内容标识、意愿表达、性健康用语、轻度亲密行为和数字时间。没有使用成人影片或露骨性行为音频。

### 完整链路

取其中前 5 段真实音频，执行“音频 → ASR 日文 → Hy-MT2 中文”，确认两套模型可以同时驻留。只测完整音频数据已经就绪后的计算时间。

**这里的 0.45～0.70 秒不是手机实时字幕的总延迟。** 它不包括等待说完、音频缓冲、VAD/断句、网络上传和手机绘制。尚未做真实连续流、长片或手机端端到端延迟测试。

## 3. 速度结果

| 测试 | 结果 | 条件 |
| --- | --- | --- |
| CPU ASR，总 49.08 秒音频 | 95.31 秒 | beam=1；本轮处理速度慢于音频播放速度 |
| GPU ASR，总 49.08 秒音频 | 4.08 秒 | beam=5，模型已预热 |
| GPU ASR，单段 | 0.34～0.53 秒 | 每段音频约 3.10～6.98 秒 |
| GPU ASR，整体实时率 RTF | 0.083 | 计算耗时 / 音频时长，约为 12 倍播放速度 |
| CPU 日译中，短句中位数 | 约 0.36 秒 | 10 组短句，模型已预热 |
| GPU 日译中，短句 | 0.063～0.120 秒 | 中位数约 0.088 秒 |
| CPU ASR + CPU 翻译，5 段链路 | 4.92～15.02 秒/段 | 音频已就绪 |
| GPU ASR + CPU 翻译，5 段链路 | 0.73～1.18 秒/段 | 音频已就绪 |
| GPU ASR + GPU 翻译，5 段链路 | **0.45～0.70 秒/段** | 中位数约 0.47 秒；音频已就绪 |

GPU ASR 模型加载约 4.71 秒，首次预热约 0.79 秒；GPU 翻译服务启动到就绪约 1.67 秒。产品中应保持模型进程运行，不能每来一句就重新加载权重。

确认全 GPU 测试时，翻译器设备列表包含 `CUDA0: NVIDIA GeForce RTX 4050 Laptop GPU`。两模型驻留并完成推理后，`nvidia-smi` 读到整机显存已用约 **5098 MiB**、空闲约 **823 MiB**。

该显存数字包含桌面和其他应用，不能当成模型独占显存，也没有做连续峰值采样。更长上下文、更长音频和多并发仍可能超出容量。

## 4. 日语识别质量

原始字符错误率的计算步骤：Unicode NFKC、转小写、去标点/空白分隔符/符号，然后计算 Levenshtein 距离。

| 设置 | 编辑错误数 / 参考字符数 | 原始 CER |
| --- | --- | --- |
| GPU，beam=1 | 27 / 196 | 13.78% |
| GPU，beam=5 | 26 / 196 | 13.27% |

**不能把这个数字直接换算成“句子准确率”。** 该计数还会惩罚 `わたし / 私`、`きのう / 昨日`、`八 / 8` 和 `所 / ところ` 等含义接近的书写差异，样本量也很小。

仍观察到至少两段明确的参考词语差异：

| 参考文本中的内容 | 实际识别 | 影响 |
| --- | --- | --- |
| `木村さん`、`写真` | `木村様`、`シャンシン` | 称谓改变，照片被识别成另一串音，后续中文出现错误人名 |
| `解毒剤` | `下毒体` | 关键词错误，不能靠提高字幕刷新速度解决 |

beam=5 修正了一处 `パック / バック` 差异，但没有修正上述主要错误。正式使用前应继续比较模型、样本和解码配置，不能只依据这 10 段宣布日语质量达标。

完整原文、识别结果与逐段时间见 `evaluation/results/asr-gpu.json`。

## 5. 中文翻译质量与已观察问题

10 组短句均返回了中文，未出现星号打码或拒答。部分例子：

| 输入 | 默认指令的输出 | 检查 |
| --- | --- | --- |
| `彼女はまだ来ていない。` | 她还没有来。 | 保留否定 |
| `くそっ、また失敗した。` | 该死，又失败了。 | 保留粗口语气 |
| `避妊具を正しく使用してください。` | 请正确使用避孕工具。 | 性健康用语有输出 |
| `嫌なら、無理に続けなくていい。` | 嫌的话，就不用勉强继续了。 | 中文生硬，不能算自然翻译 |

在真实音频链路中，即使 ASR 原文完全正确，仍出现关系反译：

```text
日语：木村さんに電話を貸してもらいました。
应表达：我从木村那里借来电话。
默认译文：借给了木村先生电话。
```

这说明翻译模型可能把动作方向翻反，不能用“成功返回了中文”替代语义验收。

## 6. 翻译指令对照

为检查上述问题，追加 6 组文本对照，比较官方形式的简短翻译指令与强调关系保真的指令：

```text
请将下面的日语对白忠实翻译为自然的简体中文。
准确保留动作执行者、接受者、借入和借出方向、否定与时间关系；
不要添加原文没有的对象。保留原文的粗口和性相关用语，
不主动打码或委婉化。只输出译文，不要解释。
```

| 现象 | 加强指令后的实际输出 | 判断 |
| --- | --- | --- |
| 向木村借来电话 | 我借了木村先生的电话。 | 这一个已知反译例子得到修正 |
| 把电话借给木村 | 我借给了木村先生电话用。 | 方向正确，措辞仍可改进 |
| 不愿意不用勉强继续 | 如果不喜欢，就不用勉强继续下去。 | 比“嫌的话”自然 |
| 粗口与性健康用语 | 对照中继续正常输出 | 只说明这些句子，不代表全部成人内容 |
| 田中给我读书 | 我让田中先生读了书。 | 谁为谁朗读的受益关系仍不够明确 |

这是针对已观察错误设计的调参对照，**不属于独立验证集上的整体准确率提升证据**。加强指令的 6 组耗时约 0.07～0.11 秒，详见 `evaluation/results/prompt-comparison.json`。

前述 5 段全链路速度仍对应默认指令，没有把单独文本对照冒充成重新完成的整段影片测试。

## 7. 对当前项目的建议

1. 保留电脑本地部署路线：本机 GPU 处理速度有余量，可继续接入现有后端。
2. ASR 先采用 beam=5 作为待评测配置；这一轮提高计算量的代价不大，但不能消除主要误识别。
3. 翻译默认改用强调施事、受事、否定和授受关系的忠实指令，再用独立新样本检查是否仍改善。
4. 对人名、片名和专有词加入可编辑词表；低置信内容保留不确定性，不根据题材补写。
5. 接入手机前，补测连续音频的分段、稳定中间结果和上下文；计算速度不能替代流式实现。
6. 使用用户愿意本地测试的实际影片片段补测配乐、耳语、多人重叠和成人对白。
7. 若误识别仍明显，再做 Qwen3-ASR 的同样样本对照；本轮没有下载或测试 Qwen3-ASR，不宣称其效果更好。

- 未测试真实成人影片或露骨性行为对白，不能保证成人内容全覆盖。
- 未测试夸克内部音频在华为手机上的实际捕获。
- 未接入 Android 正式实时字幕链路，APK 仍是演示模式。
- 未测试持续一小时、多并发、手机网络波动和模型端长期内存变化。
- 未测模型完全在 Mate 40 Pro 上独立运行。
- 未训练或微调任何模型，也没有更改权重。
